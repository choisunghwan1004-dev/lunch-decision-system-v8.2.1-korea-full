# 1. API 연계 전체 시퀀스

핵심 원칙은 **외부 API → 직접 MySQL**이 아니라,

> **외부 API → API 수집 → 원본 저장 → 데이터 표준화 → 검증 → MySQL → 관리자/사용자**

구조로 만드는 것입니다.

```text
┌─────────────────────────────────────────────────────┐
│                  외부 데이터/API                     │
├──────────┬──────────┬──────────┬──────────┬─────────┤
│ 행정구역 │  상권    │ 음식점   │ 관광    │ 지도    │
│   API    │  API     │  API     │  API    │  API    │
└────┬─────┴────┬─────┴────┬─────┴────┬─────┴───┬─────┘
     │          │          │          │          │
     └──────────┴──────────┴──────────┴──────────┘
                         ↓
                 [API Connector]
                         ↓
                 [Raw Data 저장]
                         ↓
                 [Data Normalizer]
                         ↓
                 [Data Validator]
                         ↓
                 [Duplicate Check]
                         ↓
                      [MySQL]
                         ↓
              ┌──────────┴──────────┐
              ↓                     ↓
           관리자 화면             사용자 화면
              ↓                     ↓
          CRUD/수정               검색/조회
                                    ↓
                                여행 추천
                                    ↓
                                  AI API
```

# 7. 지도 API 시퀀스

지도 API는 **원천 데이터 저장용이라기보다 검색/표시용**으로 사용하는 것을 권장합니다.

```text
사용자
 ↓
"종각 맛집"
 ↓
Backend
 ↓
MySQL
 ↓
restaurant
 ↓
latitude / longitude
 ↓
지도 API
 ↓
지도 + Marker
```

즉:

```text
MySQL = 데이터의 원본
지도 API = 지도 표현
```

으로 분리합니다.

# 10. 데이터 처리 Architecture

```text
          외부 API
             ↓
       ┌────────────┐
       │ Connector  │
       └─────┬──────┘
             ↓
       ┌────────────┐
       │ Raw Data   │
       └─────┬──────┘
             ↓
       ┌────────────┐
       │ Normalize  │
       └─────┬──────┘
             ↓
       ┌────────────┐
       │ Validate   │
       └─────┬──────┘
             ↓
       ┌────────────┐
       │ Duplicate  │
       │   Check    │
       └─────┬──────┘
             ↓
       ┌────────────┐
       │   MySQL    │
       └────────────┘
```

이 구조를 사용하는 이유는 **API마다 컬럼명과 데이터 형식이 다르기 때문**입니다.

예를 들어:

```text
API A
place_name

API B
title

API C
사업장명
```

모두 내부에서는:

```text
restaurant_name
```

으로 통일합니다.

## 21. V8.2 구현 우선순위

현재 프로젝트에서는 **아래 8개를 먼저 완성**하는 것이 좋습니다.

| 순서 | 작업                    | 결과        |
| -: | --------------------- | --------- |
|  1 | `countries`           | 국가 선택     |
|  2 | `regions`             | 시도 선택     |
|  3 | `districts`           | 시군구 선택    |
|  4 | `towns`               | 읍/면/동 선택  |
|  5 | `legal_dongs`         | 법정동 기준 완성 |
|  6 | `commercial_areas`    | 상권 등록     |
|  7 | `business_categories` | 업종 선택     |
|  8 | `restaurants`         | 음식점 등록    |

그리고 **API 수집기는 ① 행정구역 → ② 상권 → ③ 음식점 순서**로 연결하는 것이 안전합니다.

이렇게 설계하면 현재 사용자가 요구했던 **“등록 항목을 직접 타이핑하는 방식이 아니라 국가 → 시/도 → 시/군/구 → 읍/면/동 → 법정동 → 상권 → 업종 → 음식점까지 선택하는 V8.2 관리자 화면”**&#xACFC; ERD가 정확하게 연결됩니다.
